# API Data Intelligence Platform 重构方案

> 文档状态：产品与技术方案草案  
> 目标阶段：MVP 重构评审  
> 核心目标：从代码和 PRD 中沉淀 API 资产，生成并执行 P0 业务场景，形成业务系统管理视角。

## 1. 产品定位

本系统重构为一套“业务 API 资产分析与场景自动化平台”。平台以业务系统为管理边界，以 API 资产为基础，以 P0 业务场景为核心产物，通过场景执行结果形成持续可观测的业务质量视图。

核心闭环：

```text
注册业务系统
  -> 接入代码仓库或本地扫描结果
  -> 分析并沉淀 API 资产
  -> 导出 OpenAPI / Postman Collection
  -> 导入并分析 PRD
  -> 生成 P0 候选场景
  -> 匹配和编排 API
  -> 人工确认并发布场景
  -> 执行场景
  -> 记录结果、趋势和系统风险
```

## 2. 目标用户

| 角色 | 主要诉求 |
|---|---|
| 测试工程师 | 快速获得 API 合集、生成核心场景、执行并定位失败步骤 |
| 研发工程师 | 校验扫描结果、补全 API 定义、分析接口变更影响 |
| 产品经理 | 确认 PRD 中的 P0 流程、检查需求是否形成可验收场景 |
| 测试负责人 | 查看 P0 覆盖率、执行成功率、不稳定场景与阻塞风险 |
| 系统负责人 | 查看本系统 API、上下游依赖、场景参与度和健康状态 |

## 3. 产品原则

1. AI 负责生成候选、匹配 API 和解释证据，不直接发布正式场景。
2. 所有分析结果都必须可追溯到代码行或 PRD 段落。
3. API、场景和执行记录必须版本化，历史结果不能被覆盖。
4. 先建立统一 API 资产模型，再导出 OpenAPI 或 Postman，避免输出格式反向绑架扫描能力。
5. 场景执行默认只允许测试环境，连接器必须具备鉴权、超时、脱敏和安全策略。
6. 全局总览与业务系统工作空间分离；扫描、API、PRD、场景和环境资产必须归属于明确的业务系统。
7. 用户默认只能访问自己负责或被授权的业务系统，所有读取和操作都必须经过数据范围校验。

## 4. 功能范围

### 4.1 业务系统与代码源管理

业务系统是所有资产的一级归属。每个系统包含：

- 名称、编码、业务域、负责人和描述。
- 一个或多个代码源。
- 技术栈、默认分支和扫描配置。
- 测试环境连接器。
- API、场景、执行结果和上下游依赖。

代码接入支持两种模式：

#### 服务端仓库模式

- 注册 Git 仓库地址和分支。
- 服务端按任务 clone 或 pull。
- 适合团队共享和定时增量扫描。

#### 本地目录模式

- CLI 执行 `api-data scan <directory>`。
- CLI 在本地解析代码，仅上传标准化资产和必要证据。
- 适合不能由服务端直接访问的代码目录。

远程 Web 页面不直接读取用户电脑上的任意目录。页面中的“选择目录”仅适用于本地部署或配套 CLI/桌面代理。

### 4.2 代码分析与 API 资产

扫描器采用插件架构：

```text
scanner-core
  ├── scanner-go
  ├── scanner-java
  ├── scanner-node
  └── scanner-python
```

第一阶段建议优先支持团队使用最多的一到两种语言，做到路由、请求模型和响应模型的可靠提取，再扩展语言数量。

统一 API 资产至少包含：

| 字段 | 说明 |
|---|---|
| systemId | 所属业务系统 |
| method/path | HTTP 方法和路由 |
| operationId | 稳定的接口标识 |
| name/description | 接口名称和说明 |
| requestSchema | Path、Query、Header、Body 参数 |
| responseSchema | 状态码和响应模型 |
| auth | 认证要求 |
| tags/domain | 控制器、模块或业务域 |
| sourceEvidence | 文件、代码行、处理函数 |
| confidence | 分析置信度 |
| version | 资产版本 |

扫描完成后输出：

- API 清单及置信度。
- 新增、删除和签名变化。
- 无请求模型、无响应模型等待补全项。
- OpenAPI 3.x 文档。
- Postman Collection 2.1。
- Postman Environment 示例。

Postman 合集按业务域或 Controller 分组，使用 `{{baseUrl}}`、`{{token}}` 等环境变量，并包含基础状态码断言、示例请求和响应变量提取脚本。

### 4.3 多来源场景发现与 P0 场景

场景发现不依赖 PRD。平台支持四种独立入口，也允许合并证据：

| 入口 | 适用情况 | 主要产物 |
|---|---|---|
| 代码挖掘 | 没有 PRD，已有可扫描代码 | 状态流转、API 链路、候选业务流程 |
| 一句话需求 | 只有口头或简短需求 | 业务意图、目标状态、API 检索结果、待补信息 |
| PRD 文档 | 有较完整需求文档 | 需求事实、验收标准、优先级和文档证据 |
| 场景包导入 | 已在本地或其他工具完成编排 | 可复用步骤、变量、断言和执行配置 |

#### 代码挖掘

代码扫描完成后，场景分析器进一步读取：

- 路由、Handler、Service 和 Repository 调用关系。
- 状态常量、状态判断与状态赋值。
- API 请求输出与其他 API 请求输入的字段关系。
- HTTP/RPC 客户端、消息生产与消费、事件处理器。
- 单元测试、集成测试、Fixture 和示例数据。
- 数据库事务边界和关键业务校验。

分析器从这些证据中构建业务状态图和可能的 API 顺序，例如：

```text
CreateOrder -> AuditOrder -> PushToWms -> CreateOutbound -> AllocateInventory
```

代码生成的候选场景必须显示调用链、状态流转、代码文件和行号，并明确区分“代码确定事实”和“AI 推断关系”。

#### 一句话需求

用户可以直接输入类似：

```text
销售订单审核后生成出库单并完成库存分配
```

平台从一句话中识别业务实体、动作、目标状态和参与系统，再从当前系统 API 资产及调用图中检索组合。缺少 PRD 时，系统把未确定的信息标记为待补充项，而不是阻止生成候选。

一句话需求生成结果至少包含：

- 解析出的目标和假设。
- 推荐 API 顺序。
- 参数依赖和前置数据。
- 目标断言。
- 置信度及待确认问题。

#### PRD 文档

PRD 是可选的增强证据。第一阶段输入 Markdown 和纯文本，第二阶段扩展 DOCX、PDF。

PRD 被解析为“需求事实”，需求事实包括：

- 业务目标。
- 参与系统和角色。
- 业务实体。
- 前置条件。
- 触发动作。
- 状态流转。
- 预期结果。
- 异常约束。
- 优先级和文档证据。

#### 导入本地编排场景

用户可以导入已经在本地或其他工具编排完成的 JSON 场景。平台支持两类格式：

1. 原生 Scenario Bundle：完整表达系统归属、API 引用、步骤依赖、变量提取、断言、超时和失败策略。
2. Postman Collection 2.1：兼容已有请求目录、变量、Pre-request Script 和 Test Script，并转换成平台步骤。

推荐以原生格式作为无损交换协议，Postman 作为高兼容导入格式。Postman 中无法可靠转换的 JavaScript 脚本必须保留原文并标记“需要人工转换”，不能静默忽略。

原生场景包结构示例：

```json
{
  "schemaVersion": "1.0",
  "scenario": {
    "name": "销售订单库存分配",
    "ownerSystem": "oms",
    "participantSystems": ["wms"],
    "priority": "P0"
  },
  "steps": [
    {
      "id": "create_order",
      "request": {
        "method": "POST",
        "url": "{{omsBaseUrl}}/api/order/create"
      },
      "extract": {
        "orderNo": "$.data.orderNo"
      }
    }
  ]
}
```

导入流程：

```text
选择 JSON 文件
  -> 识别格式与版本
  -> 预览步骤和变量
  -> 绑定业务系统与平台 API 资产
  -> 检查环境变量、脚本和敏感信息
  -> 人工确认转换差异
  -> 保存为 DRAFT 场景版本
  -> 试运行后发布
```

导入不能直接产生已发布场景。即使格式完全合法，也必须经过以下安全检查：

- URL 是否属于已授权业务系统。
- 请求方法是否命中安全黑名单。
- 是否携带明文 Token、Cookie、密码或真实数据。
- 变量是否能够绑定到平台环境或上下文。
- 脚本是否包含平台不允许的网络、文件或动态执行能力。
- API 是否能匹配已有资产；不能匹配时创建“未绑定步骤”。
- 场景 ID 冲突时由用户选择新建、覆盖草稿或导入为新版本。

P0 由规则评分和 AI 判断共同决定。判定信号包括：

- PRD 明确标记 P0、必须或核心流程。
- 属于交易、支付、履约、库存、结算等主链路。
- 失败会阻断交易或导致资金、库存、账务错误。
- 跨系统关键数据同步。
- 验收标准明确要求必须通过。
- 高频且影响面较大的 Happy Path。

无论来源是什么，每个候选场景必须展示：

- P0 判定理由。
- 证据来源；可以是代码调用链、测试代码、一句话需求或 PRD 段落。
- 参与系统。
- 前置数据。
- 目标结果。
- 已匹配 API、状态流转和匹配置信度。
- 缺失 API、参数或断言。

同一候选场景可以合并多个来源，例如“代码发现 + 一句话确认”或“代码发现 + PRD 证据”。证据越多，置信度可以提高，但正式场景仍需人工核验。

### 4.4 API 检索与场景编排

API 匹配不只依赖文本相似度，还需要结合：

- 业务实体与动作。
- 请求参数和响应字段。
- 状态枚举与状态流转。
- Handler、Service 调用关系。
- 上一步输出与下一步输入的兼容关系。
- API 所属系统及上下游依赖。

场景编排器输出可人工编辑的有向步骤链。每个步骤支持：

- API 引用和版本。
- 请求参数模板。
- 上下文变量引用。
- 前置条件和跳过条件。
- 响应变量提取。
- 状态与字段断言。
- 超时、重试和失败策略。
- 补偿步骤。
- 适用目标阶段。

场景生命周期：

```text
DRAFT -> REVIEWING -> PUBLISHED -> DEPRECATED
```

候选场景必须经过人工确认后才能发布和进入定时执行。

#### 场景创建与编辑交互

场景编排采用四步引导，避免用户直接面对空白画布：

1. 基本信息：名称、主责系统、参与系统、优先级和来源 PRD。
2. 添加步骤：从已匹配 API、当前系统 API 或自定义操作中加入步骤。
3. 配置步骤：逐个设置请求映射、变量提取、断言、超时和失败策略。
4. 校验发布：检查依赖、缺失参数、权限和环境可执行性，保存为新版本。

画布中的每个步骤必须提供独立操作：

- `编辑`：只打开并修改当前步骤，不影响其他步骤。
- `单步执行`：使用已准备的上下文运行当前步骤。
- `执行到此`：从第一步开始运行，并在当前步骤完成后停止。
- `从此处继续`：基于某次运行保存的上下文，从当前步骤继续。
- `复制`：复制当前步骤并保留配置。
- `禁用/启用`：临时跳过步骤，不删除配置。
- `删除`：删除步骤前展示上下游变量影响。

右侧步骤编辑器应明确显示“正在编辑步骤 N”，并采用请求、参数映射、变量提取、断言和高级设置等标签页。点击“保存当前步骤”只更新当前步骤草稿；整场“保存草稿”或“发布版本”另设入口。

#### 部分执行与目标步骤

场景支持以下执行范围：

| 模式 | 行为 |
|---|---|
| 完整执行 | 从第一步执行到最后一步 |
| 执行到指定步骤 | 从第一步开始，在指定步骤成功后停止 |
| 单步执行 | 仅执行选中步骤，需要手工参数或已有上下文 |
| 从失败步骤重试 | 复用原运行的脱敏上下文，从失败步骤继续 |
| 从指定步骤继续 | 仅 Owner/Runner 可用，必须选择可复用的上下文快照 |

“执行到此”是正式的运行配置，不等同于简单截断步骤列表。执行引擎需要记录 `target_step_id`，只运行目标步骤所需的前置步骤和适用断言，避免当前原型中无条件追加全部校验步骤的问题。

### 4.5 场景执行与结果记录

执行入口包括：

- 控制台手动执行。
- REST API。
- CLI。
- 定时任务。
- CI/CD Webhook。
- 批量参数化任务。

场景执行采用异步任务：

```text
POST /api/runs                  创建运行，返回 runId
GET  /api/runs/:runId           查询运行结果
GET  /api/runs/:runId/events    获取实时步骤事件
POST /api/runs/:runId/cancel    取消运行
POST /api/runs/:runId/retry     从失败步骤重试
```

执行数据拆分为：

| 数据对象 | 主要内容 |
|---|---|
| scenario_run | 场景、版本、环境、触发人、总状态、总耗时 |
| step_run | 步骤请求、响应摘要、状态、耗时和错误 |
| assertion_result | 实际值、期望值、运算符和断言结果 |
| extracted_variable | 提取变量名、脱敏值和来源步骤 |

执行引擎必须实现：

- 连接器认证。
- 单步和整场超时。
- 有边界的失败重试。
- 运行取消。
- 请求和响应脱敏。
- 日志大小控制与归档。
- 黑白名单和环境隔离。
- 并发控制和幂等保护。

### 4.6 业务系统管理驾驶舱

管理视角需要回答：

- 已接入多少业务系统和代码仓库？
- 每个系统有多少 API，最近是否发生变化？
- P0 需求有多少，已形成多少可执行场景？
- 哪些系统或场景持续失败？
- 哪个系统是跨系统主链路的高风险节点？
- 哪些 API 变更影响了已发布场景？

核心指标：

| 视角 | 指标 |
|---|---|
| 系统资产 | 系统数、仓库数、API 数、最近扫描时间 |
| API 质量 | 模型识别率、文档完整率、低置信 API、变更数量 |
| 场景覆盖 | P0 需求数、已发布场景数、可执行率、系统覆盖率 |
| 执行健康 | 成功率、平均耗时、失败趋势、不稳定场景 |
| 变更影响 | 新增/删除 API、签名变化、受影响场景 |
| 治理风险 | 无鉴权 API、无断言步骤、无超时连接器、失效接口 |

## 5. 信息架构

平台采用“两层工作空间”：

- 全局管理空间：面向平台管理员、测试负责人和管理者，展示跨系统概况。
- 业务系统空间：面向系统负责人、研发和测试，处理某个系统内部的资产、场景、环境和运行。

```text
全局管理空间
├── 工作台
│   ├── 系统全景
│   ├── P0 覆盖
│   ├── 风险与待办
│   └── 跨系统运行趋势
├── 业务系统
│   ├── 我负责的系统
│   ├── 我参与的系统
│   └── 全部系统（管理员）
├── 全局运行记录
├── 全局运行详情
└── 平台权限管理（管理员）

业务系统工作空间
├── 系统概况
│   ├── 基本信息与负责人
│   ├── API / 场景 / 运行指标
│   ├── 上下游依赖
│   └── 风险与待办
├── 代码与 API
│   ├── 代码源
│   ├── 代码扫描任务
│   ├── API 资产库
│   ├── API 变更
│   └── Postman / OpenAPI 导出
├── 场景发现与管理
│   ├── 代码场景挖掘
│   ├── 一句话需求
│   ├── PRD 文档（可选）
│   ├── 场景包 / Postman JSON 导入
│   ├── P0 场景候选
│   ├── 场景人工核验
│   ├── 场景编排
│   └── 已发布场景
├── 执行与环境
│   ├── 系统运行记录
│   ├── 环境与连接器
│   ├── 测试数据配置
│   └── 定时任务
└── 系统设置
    ├── 成员与角色
    ├── 密钥引用
    ├── 安全策略
    └── 系统操作日志
```

页面顶部始终展示“当前业务系统”选择器。切换系统后，代码扫描、API、PRD、场景和运行数据必须一起切换，不能只做前端筛选。

### 5.1 单系统场景人工核验工作台

场景候选进入正式编排前，需要经过一个独立的人工核验工作台。页面采用三栏结构：

1. 左栏：本系统待核验场景、优先级和处理状态。
2. 中栏：PRD 事实、业务流程、前置条件、预期结果和 P0 判定原因。
3. 右栏：匹配 API、代码证据、上下游系统、参数缺口和风险。

核验人可以执行：

- 确认或调整 P0/P1 优先级。
- 接受、替换或移除匹配 API。
- 补充前置条件、测试数据和断言。
- 标记跨系统协作人。
- 退回重新分析。
- 确认后进入场景编排。

### 5.2 单系统具体操作

系统工作空间必须提供明确的业务操作入口：

- 发起或取消代码扫描。
- 查看扫描差异并确认 API。
- 导出本系统 Postman/OpenAPI。
- 导入和重新分析本系统 PRD。
- 核验、编排、发布和下线场景。
- 配置连接器并执行健康检查。
- 发起试运行、重试失败步骤、取消运行。
- 邀请成员、调整角色、查看操作审计。

所有危险操作应显示影响范围，并要求相应角色权限。

## 6. 权限与数据隔离

权限模型采用“平台角色 + 系统成员角色 + 资源操作”三层控制。

### 6.1 平台角色

| 角色 | 权限范围 |
|---|---|
| 平台管理员 | 管理所有系统、用户、平台策略和全局数据 |
| 管理查看者 | 查看跨系统总览与汇总结果，不可修改系统资产 |
| 普通用户 | 只能进入已授权业务系统 |

### 6.2 系统成员角色

| 角色 | 主要权限 |
|---|---|
| 系统负责人 Owner | 系统内全部权限、成员和发布审批 |
| 维护者 Maintainer | 扫描、API 确认、环境和场景维护 |
| 核验者 Reviewer | PRD/P0 场景核验、审核和退回 |
| 执行者 Runner | 发起执行、重试和查看完整运行结果 |
| 查看者 Viewer | 只读查看脱敏后的资产与结果 |

一个用户可以在不同系统拥有不同角色。例如，用户可以是 OMS 的 Owner、WMS 的 Viewer，同时完全看不到 PAY 系统。

### 6.3 数据范围

每个领域对象都必须携带 `system_id`，包括：

- 代码源和扫描任务。
- API、模型和变更记录。
- PRD、需求事实和候选场景。
- 场景、版本和步骤。
- 环境、连接器和密钥引用。
- 运行、步骤日志和断言结果。

服务端每次查询和写操作都根据当前用户的系统成员关系过滤。前端隐藏菜单不构成权限控制。

跨系统场景采用“主责系统 + 参与系统”模型：

- 主责系统负责场景版本和发布。
- 参与系统的 Reviewer 确认涉及本系统的 API、参数和断言。
- 用户只能看到自己有权限系统对应的敏感请求、响应和环境信息。
- 全局运行列表对无权限系统只展示脱敏汇总，或完全不可见，具体由平台策略决定。

### 6.4 操作审计

以下操作必须记录操作者、时间、系统、对象、变更前后值和来源 IP：

- 系统成员和角色调整。
- 连接器和密钥引用修改。
- API 人工确认。
- 场景核验、发布和下线。
- 生产敏感环境操作。
- 运行取消、强制重试和日志导出。

## 7. 技术架构建议

建议从当前单进程、JSON 文件存储和单 HTML 页面，重构为清晰的模块化单体；在业务量明确前不急于拆微服务。

```text
apps/
  web/                  管理控制台
  api/                  后端 API
  worker/               扫描、分析和执行任务
  cli/                  本地目录扫描

packages/
  domain/               统一领域模型
  scanner-core/         扫描框架
  scanner-go/           Go 插件
  scanner-java/         Java 插件
  prd-analyzer/         PRD 解析与 P0 判断
  api-catalog/          API 资产与变更管理
  scenario-engine/      API 匹配和场景编排
  execution-engine/     场景执行
  postman-exporter/     OpenAPI/Postman 导出
```

建议技术选择：

| 层级 | 建议 |
|---|---|
| Web | React + TypeScript，使用成熟组件库 |
| API/Worker | Node.js + TypeScript，保留与现有项目的迁移连续性 |
| 数据库 | PostgreSQL |
| 任务队列 | MVP 可使用 PostgreSQL Job；规模扩大后再引入 Redis/BullMQ |
| 对象存储 | 保存 PRD 原件、大型报告和导出文件 |
| 实时状态 | SSE，满足运行步骤流式更新 |
| 扫描器 | AST/框架插件优先，正则仅作为兜底 |

## 9. MVP 实施路线

### 里程碑一：API 资产闭环

- 业务系统与代码源注册。
- 登录、系统成员关系和数据范围隔离。
- 一种主力语言的 AST 扫描。
- API 资产列表、详情和证据。
- OpenAPI/Postman 导出。
- 扫描历史和 API 变更。

### 里程碑二：P0 场景闭环

- Markdown/TXT PRD 导入。
- 需求事实和 P0 候选生成。
- API 检索和匹配。
- 可视化步骤编排。
- 场景审核和版本发布。

### 里程碑三：执行闭环

- 环境和连接器管理。
- 异步场景执行。
- 断言、变量提取、超时和脱敏。
- 运行列表和运行详情。
- 失败步骤重试。

### 里程碑四：管理驾驶舱

- 系统全景指标。
- P0 覆盖率。
- 执行成功率和趋势。
- API 变更影响。
- 风险和待办中心。

## 10. MVP 验收标准

1. 用户能注册一个代码仓库并完成扫描。
2. 平台能展示带代码证据的 API 资产，并导出可导入 Postman 的合集。
3. 用户能上传一份 PRD，并得到带文档证据的 P0 场景候选。
4. 用户能确认候选场景、调整 API 顺序和参数映射并发布版本。
5. 用户能在测试环境执行场景并实时查看步骤状态。
6. 运行结束后能查看请求摘要、响应摘要、断言、耗时和错误。
7. 管理工作台能展示系统、API、P0 覆盖和运行健康概况。
8. 普通用户只能查看被授权的业务系统，且不同系统可以拥有不同角色。
9. 系统 Reviewer 能在独立页面完成 P0 场景人工核验并留下审核记录。

## 11. 待确认决策

进入详细设计前，需要确认：

1. 第一阶段优先支持的代码语言和框架。
2. 代码源以 Git 仓库为主，还是必须优先支持本机目录。
3. PRD 首批格式是否只做 Markdown/TXT。
4. 是否需要接入现有用户和权限体系。
5. P0 场景是否必须经过产品、研发、测试多角色审批。
6. 测试环境连接器的密钥由哪个现有系统托管。
7. 第一阶段是否需要 CI/CD 和定时执行。
