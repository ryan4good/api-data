## 1. 背景

测试、联调、问题复现和演示过程中，业务数据准备高度依赖人工理解系统逻辑、拼参数、调接口、查状态。随着业务系统增多，造数成本集中体现在：

- 不同系统的业务流程、状态流转、接口参数分散在代码和经验里。
- 造数经常需要跨 OMS、WMS、TMS、财务、售后等多个系统。
- 使用者只知道“我要一笔某状态的数据”，但不知道该调哪些接口、前置条件是什么。
- 新业务系统接入后，平台需要快速理解代码、生成 P0/E2E 场景，并让业务 Owner 校正确认。

本产品目标是建设一个 AI 造数平台：用户用自然语言描述需要的数据，平台自动选择场景、组织参数、生成执行计划、调用接口、校验结果，并沉淀业务系统的 E2E 场景资产。

## 2. 产品目标

### 2.1 核心目标

1. 提升造数效率：从“人工查代码、拼接口、查结果”变成“自然语言输入、一键预览、一键执行”。
2. 扩大业务覆盖：支持多个业务系统接入，并按系统统计 P0/P1 场景覆盖率。
3. 快速接入新系统：扫描业务系统代码，生成接口资产、状态机、调用链和 E2E 候选场景。
4. 保证结果可信：每个场景必须有参数槽位、步骤编排、目标状态、校验点、证据链和执行日志。
5. 控制执行风险：通过环境、权限、黑名单、审批、审计、试运行机制控制造数风险。

### 2.2 非目标

- v0.2 不直接支持生产环境写数据。
- v0.2 不做完整低代码编排器，只提供场景校正所需的关键操作。
- v0.2 不承诺完全自动理解所有代码逻辑，AI 生成的候选场景必须经过确认。
- v0.2 不替代测试用例管理平台，只管理“造数场景”和“执行结果”。

## 6. 核心业务流程

### 6.1 新业务系统接入流程

目标：让一个新业务系统从“代码仓和测试环境”进入平台，产出可校正、可试运行的 E2E 候选场景。

```text
注册系统 -> 配置连接器 -> 扫描代码 -> 分析资产 -> 生成 E2E 候选 -> 人工校正 -> 试运行 -> 发布正式场景
```

#### 步骤 1：注册业务系统

必填字段：

| 字段 | 说明 | 示例 |
| --- | --- | --- |
| systemCode | 系统唯一编码 | rma |
| systemName | 系统名称 | 售后服务系统 |
| owner | 系统负责人 | RMA Owner |
| repoUrl | 代码仓地址 | git@example.com:biz/rma-service.git |
| branch | 扫描分支 | main |
| backendStack | 后端技术栈 | Go / Gin |
| frontendStack | 前端技术栈 | React |
| appStack | App 技术栈 | Flutter |
| env | 环境 | test |
| baseUrl | 测试环境地址 | http://rma-test.internal |
| authType | 认证方式 | Bearer Token |

验收标准：

- 系统编码不可重复。
- 必填字段缺失时不可提交。
- 提交后系统出现在“业务系统列表”和“治理配置/连接器安全”。
- 未通过连接器健康检查的系统不可执行造数。

#### 步骤 2：配置连接器

连接器字段：

| 字段 | 说明 |
| --- | --- |
| systemCode | 归属系统 |
| env | dev/test/pre/prod |
| baseUrl | 接口地址 |
| auth.type | none/token/basic/custom |
| auth.secretRef | 密钥引用，不在前端明文展示 |
| timeoutMs | 单接口超时时间 |
| retryPolicy | 重试次数和退避策略 |
| blacklist | 禁止调用的接口 |
| allowWrite | 是否允许写接口 |
| auditEnabled | 是否记录审计日志 |

验收标准：

- test 环境可配置写接口。
- prod 环境默认禁止写接口。
- 黑名单命中的步骤在 dry-run 阶段被拦截。
- 连接器密钥不在页面和日志明文展示。

#### 步骤 3：代码扫描

输入：

- 代码仓地址、分支、扫描目录。
- 技术栈类型：Go、Java、Node、Vue、React、App。
- 系统类型：业务系统、网关、任务系统、消息消费者。

扫描产物：

| 产物 | 说明 |
| --- | --- |
| API 清单 | method、path、handler、request、response |
| 实体模型 | entity、field、数据库表、DTO |
| 状态机 | status 字段、状态枚举、状态流转函数 |
| 服务调用图 | controller -> service -> repository |
| 跨系统依赖 | HTTP、RPC、MQ、SDK 调用 |
| 业务关键词 | order、outbound、refund、shipment 等 |
| 候选场景证据 | 场景步骤对应的代码文件、行号、接口 |

验收标准：

- Go 后端至少识别 controller、service、route、DTO、status 常量。
- 前端 Vue/React 至少识别页面路由、接口调用、表单字段。
- App 端至少识别接口调用、页面路径和关键业务操作。
- 扫描结果必须能落库并可追溯到代码证据。

### 6.2 E2E 场景生成流程

目标：基于扫描产物自动生成端到端候选业务场景。

输入：

- API 清单。
- 实体模型。
- 状态机。
- 跨系统依赖。
- 业务关键词。
- 历史执行日志。
- 平台内置 P0 场景模板。

输出：候选场景。

候选场景字段：

| 字段 | 说明 |
| --- | --- |
| sceneId | 场景 ID |
| name | 场景名称 |
| systems | 涉及系统 |
| priority | P0/P1/P2 |
| confidence | 置信度 |
| intentSamples | 可命中的自然语言样例 |
| preconditions | 前置条件 |
| params | 参数槽位 |
| targetStage | 目标阶段 |
| steps | 执行步骤 |
| validations | 结果校验点 |
| evidence | 代码证据链 |
| riskLevel | 风险等级 |

置信度计算：

| 因子 | 权重 |
| --- | --- |
| 创建接口、推进接口、查询接口齐全 | 25% |
| 能识别状态机和目标状态 | 20% |
| 参数可从模板或前置步骤补齐 | 20% |
| 跨系统链路证据完整 | 20% |
| 历史日志或人工确认增强 | 15% |

验收标准：

- 候选场景必须至少包含 1 个创建步骤和 1 个校验步骤。
- 跨系统 E2E 场景必须展示系统顺序和依赖关系。
- 低于 60% 置信度的候选进入“低置信待分析”，不可直接确认。
- 每个候选步骤都必须能展示接口证据或人工补充原因。

### 6.3 场景校正流程

目标：让业务 Owner 或使用者把候选场景校正成可执行的正式场景。

操作区：

| 区域 | 支持操作 |
| --- | --- |
| 参数映射 | 新增参数、修改默认值、绑定前置步骤产物、设置必填/可选 |
| 步骤校正 | 调整顺序、启用/停用步骤、设置 stopAfter、补充接口 |
| 状态校正 | 设置目标阶段、状态枚举、状态流转条件 |
| 校验点 | 新增查询接口、断言字段、断言表达式 |
| 证据链 | 查看代码证据、补充人工证据、标记证据不足 |
| 执行护栏 | 设置风险等级、审批规则、黑名单、数量限制 |

候选场景状态：

```text
待校正 -> 待试运行 -> 试运行通过 -> 已发布
       -> 已驳回
       -> 证据不足
```

验收标准：

- 未设置目标阶段的场景不可试运行。
- 必填参数没有默认值或来源时不可试运行。
- 没有校验点的场景不可发布。
- 校正后必须生成版本记录。
- 发布前必须由业务系统 Owner 确认。

### 6.4 试运行流程

目标：在发布正式场景前验证可执行性和安全性。

流程：

```text
连接器预检 -> 参数补齐 -> dry-run -> 单步执行 -> 结果校验 -> 报告生成 -> 发布确认
```

试运行能力：

| 能力 | 说明 |
| --- | --- |
| 连接器预检 | 检查 baseUrl、auth、超时、健康接口 |
| 参数补齐 | 从模板、意图、前置步骤产物补齐参数 |
| dry-run | 不发起写请求，只检查计划、权限、黑名单、环境 |
| 单步执行 | 按步骤执行，可停在某一步 |
| 断点续跑 | 从失败步骤或指定步骤继续 |
| 失败重试 | 按步骤配置重试策略 |
| 结果校验 | 执行查询接口和断言 |
| 报告输出 | 输出单号、状态、耗时、失败原因、证据链 |

验收标准：

- dry-run 必须展示将调用的系统、接口、参数、风险。
- 试运行失败必须展示失败步骤、请求、响应、错误原因。
- 试运行通过后才能进入发布确认。
- 试运行报告可在执行日志中追溯。

### 6.5 正式执行流程

用户输入：

```text
我需要造一笔销售订单并生成出库单，先做到分配库存完成
```

系统处理：

```text
解析意图 -> 匹配场景 -> 补齐参数 -> 生成计划 -> 用户预览 -> 执行 -> 校验 -> 返回结果
```

结果输出：

| 字段 | 说明 |
| --- | --- |
| success | 是否成功 |
| scene | 命中的场景 |
| targetStage | 目标阶段 |
| context | 业务结果，如 orderNo、outboundNo |
| logs | 每一步请求、响应、耗时 |
| validations | 校验结果 |
| error | 失败原因 |

验收标准：

- 自然语言能命中正式场景。
- 用户能在执行前看到计划预览。
- 用户可以选择目标阶段。
- 执行成功后返回关键业务单号。
- 执行失败后能定位到步骤和接口。

- 密钥管理。
- 定时扫描。
- 场景推荐。
- 执行报表。
- 与 CI/CD 或测试平台集成。

## 12. 验收标准

### 新系统接入

- 能创建一个新业务系统。
- 能配置测试环境连接器。
- 能触发代码扫描。
- 能看到扫描产物。
- 能生成至少 1 个候选 E2E 场景。

### 候选场景校正

- 能编辑参数槽位。
- 能调整步骤顺序。
- 能设置目标阶段。
- 能增加校验点。
- 能查看和补充证据链。
- 能确认或驳回候选场景。

### 试运行

- 能执行 dry-run。
- 能展示接口调用计划。
- 能发现黑名单、权限、参数缺失问题。
- 能单步执行试运行。
- 能生成试运行报告。

### 正式造数

- 能通过自然语言命中场景。
- 能预览执行计划。
- 能执行到指定阶段。
- 能返回业务单号。
- 能记录完整日志。

## 13. 风险和待确认问题

| 问题 | 风险 | 建议 |
| --- | --- | --- |
| 代码扫描准确率不足 | 候选场景质量低 | 先聚焦 Go 后端和 P0 场景 |
| 多系统鉴权复杂 | 接入成本高 | 连接器统一抽象，密钥引用管理 |
| 执行造数污染环境 | 影响测试数据 | 环境矩阵、黑名单、审批、清理策略 |
| 参数自动补齐失败 | 执行成功率低 | 参数模板 + 前置步骤产物绑定 |
| AI 误生成场景 | 风险不可控 | 候选必须人工确认后发布 |
| 业务 Owner 不维护 | 覆盖率难提升 | 缺口队列和 Owner 视图绑定 |
